# 2026-07-10

## Refrigeration power metering with a Tasmota S31

Added a Sonoff S31 at `192.168.0.210` between the inverter-fed receptacle and
the refrigeration load. It had already been reflashed with current Tasmota.
Selected module **Sonoff S31 (41)**, then set `DeviceName` and `FriendlyName1`
to `Refrigeration` and hostname to `s31-refrigeration`.

The first direct HTTP tests were awkward: Tasmota's Referer check made `/cm`
look dependent on a live browser tab even after the tab was gone. The durable
fix was `SetOption128 1`, which permits ordinary trusted-LAN HTTP requests. The
supervisor reader still sends a same-device Referer, but no longer depends on
browser state. Set `TelePeriod 60`; this is Tasmota's own telemetry interval,
not the supervisor poll cadence.

Configured site-local Eastern rules with custom timezone 99:

```text
Timezone 99
TimeStd 0,1,11,1,2,-300
TimeDst 0,2,3,1,2,-240
```

The device gets wall time from its configured Internet NTP servers. Its
`ENERGY.Today` counter resets automatically at local midnight and can be forced
to zero with `EnergyToday 0`; there is no battery-backed RTC in the S31, so the
counter boundary after a no-WAN cold boot remains a known limitation.

Commit `17a1f35` added generic `TASMOTA_DEVICES` registration, read-only
`Status 10` polling, generic `monitored_loads` API output, and durable sources
named `tasmota.<key>`. The live cadence is five seconds, matching the main
supervisor readers; SQLite persistence remains the system-wide 60-second
cadence. Three-hour power averages are re-seeded from the metric store after a
restart.

The displays now append `(Refrigeration NNNW)` to the Load group's Now and 3hr
Rolling Avg lines and `(Refrigeration N.nkWh)` to Cumulative Today on terminal,
API-terminal, browser, and Kindle renderers. The display lookup is specifically
keyed to `refrigeration`; generic registration of a future S31 provides logging
and API data but does not silently add another annotation.

The repeatable expansion procedure now lives in
[Adding a Tasmota Sonoff S31](../runbooks/add-tasmota-s31.md), with architecture
and limitations in [Individual load metering](../subsystems/load-metering.md).

## Finding a durable clock for WAN-less Pi boot

Investigated what could provide time after a complete battery-bank shutdown
when the Pi reboots without Internet. The Pi has no `/dev/rtc`; the
`systemd-timesyncd` clock file is a persisted lower bound, not a ticking clock.
No usable RTC is exposed by the Cubix CAN/RS485 telemetry, and the EPEver clock
has not been reliable enough to serve as authority.

The Classic has two relevant clocks: a main-board clock powered while battery
input is present, and the MNGP's CR1216 coin-cell-backed RTC. `TMSYNC` transfers
MNGP time to the main board. Reading Modbus registers 4214-4218 produced
`2026-07-10 19:25:05 EDT`; comparison at the Pi midpoint showed the Classic
about 32.4 seconds slow. Register 4218's day-of-year was stale (`59`) despite
correct date fields, so it cannot be part of validation.

Tried writing the CTIME registers after the documented Ethernet unlock. Modbus
acknowledged the request, but immediate readback was unchanged. For this
firmware the external registers are effectively read-only and, crucially, do
not offer a path to write the durable MNGP RTC. Time correction therefore
remains a front-panel operation.

Commit `e512eb2` deployed an NTP-first boot helper. It waits briefly for normal
Internet time, reads and validates the Classic's site-local RTC only if NTP is
absent, and may advance—but never rewind—the Pi. It ignores register 4218,
rejects gross dates and forward steps, runs with only `CAP_SYS_TIME`, and fails
open so an absent Classic does not hold telemetry down. Detailed rationale and
operations are in
[System timekeeping and Classic/MNGP recovery](../subsystems/timekeeping.md).
