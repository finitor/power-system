## Classic VOC as irradiance proxy while charging is disabled

Ongoing question: when pack temperature drops below 0 °C and charging is
disabled entirely, what signal tells us whether the sun is strong enough to
justify running the 200 W battery heater? The EPEver coil is open; the Classic
trickles at its floor. Neither output current is informative.

**Investigation:** Pulled historical telemetry correlating `last_voc` (Classic
register 4122) and `pv_voltage` (4116) with power output during Bulk charging.
Filtered to periods with allocator target ≥ 25 A to exclude severely
current-limited samples. Result: 130–132 V `last_voc` is the zone where ≥ 200 W
output becomes likely; 134 V+ is the zone where it is nearly certain.

**Experiment (2026-06-26):** Used the new allocation override API
(`allocation-override.py limit 0 0`) to cap Classic output at 0 A while the
supervisor and telemetry kept running. Observed `last_voc` updating every ~60
seconds and tracking passing clouds in real time (131.4 → 130.6 → 131.4 → 131.2
→ 131.0 → 129.8 over eight minutes). **Conclusion confirmed: `last_voc` is
independent of charge state.** The Classic performs VOC sweeps internally as
part of its MPPT algorithm and records them to register 4122 continuously
regardless of its current-limit register or the BMS charge-enable state.

`pv_voltage` also tracks near-VOC levels whenever Classic output is near zero,
making it a real-time second proxy for the same irradiance signal.

**Proposed heater heuristic** (not yet automated):

1. Pack temperature ≤ 0 °C
2. Current time between sunrise and sunset
3. `pv_voltage` or `last_voc` > 132 V

Documented in `docs/charge-management.md` under "Cold-Weather Operation."

**SQLite ownership incident:** Running `sqlite3` as the `tvetter` user
re-creates the WAL and SHM files with wrong ownership, blocking the `offgrid`
supervisor from writing. Fix: always use `sudo -u offgrid sqlite3 ...` to query
the database interactively. Restarting the supervisor after fixing ownership
(`sudo chown offgrid:offgrid metrics.sqlite-shm metrics.sqlite-wal`) restores
writes and the fallback buffer merges automatically.

## Relay board — GPIO control for heater/fan and Classic charge disable

**What shipped (`6c0b2e4`, `108cf5d`, `31d51d7`, `6d9114d`):**

Hardware: Javino 2-channel optocoupler-isolated relay module (SRD-05VDC-SL-C), jumpers S1/S2 set HIGH (high-level trigger = fail-off). Driven from Pi BCM GPIO:

| Pi pin | GPIO (BCM) | Relay CH | Function |
|---|---|---|---|
| Pin 11 | GPIO 17 | CH1 | `heat_fan` — 12 V fan + SSR heater control |
| Pin 13 | GPIO 27 | CH2 | `charge_disable` — Classic AUX2 charge inhibit |

**`relay.py` (`RelayController`):** lazy blinka/gpiod GPIO initialisation, stub fallback when hardware is absent. HTTP API endpoint `GET /api/v1/relay/state` and `POST /api/v1/control/relay`. Confirmed on Pi: `"stub": false` (real GPIO active).

**`relay_control.py` (`RelaySupervisor`):** called each supervisor tick, two independent channels:

- **`heat_fan` (CH1):** hysteresis on minimum cell temperature (CAN frame 0x373) with VOC as irradiance gate. Cut-in: min cell temp < 2 °C AND Classic VOC > 134 V. Cut-out: temp > 5 °C OR VOC < 130 V. (Temporary dry-run thresholds 17.5 / 20 °C set later in the session — revert before winter.) VOC thresholds are irradiance proxy; 2 V hysteresis band gives headroom above Classic's MPPT noise.

- **`charge_disable` (CH2):** mirrors the effective Classic target after AllocationOverride is applied. Fires when `classic_target.disable == True` OR `classic_target.target_current_a == 0.0`. A manual ceiling of 0 A via the allocation API also fires the relay. When the relay closes, 12 V is applied to Classic AUX2+ (>6 V threshold), forcing the Classic to Resting independent of any Modbus write.

**AUX2 wiring design (not yet physically wired as of this date):**

- Relay CH2 COM → 12 V supply (GND common with Classic system negative)
- Relay CH2 NO → Classic AUX2+ terminal
- Classic AUX2− → GND

Classic AUX2 must be reconfigured from WhizBang Jr (function 18) to "Active HIGH input turn off" (function 15, register 4165 = 0x4F01) before wiring is live. WhizBang Jr is currently on AUX2 and must be removed first.

**CH1 physical wiring design (not yet wired):**

- Relay CH1 COM → 12 V bus
- Relay CH1 NO → MRD-060D10 SSR control+ (pin 3) and 12 V fan+ in parallel
- SSR control− and fan− → common GND
- SSR output switches 48 V heater load (1–60 VDC / 10 A; control input 4–32 VDC)

Pi GPIO is 3.3 V — cannot drive the SSR directly (4 V minimum). The relay provides the 12 V drive. Relay CH1 tested successfully 2026-06-26 by toggling for 30 s and observing a 12 VDC fan spin.

**Bench validation done this session:**

- GPIO 17/27 confirmed via indicator LEDs
- Manual CCL override to 0 A confirmed charge_disable relay fires
- `GET /api/v1/relay/state` returns `{"stub": false, "heat_fan": false, "charge_disable": false}` on Pi

## Allocation override API

Built a supervisor-resident control surface for temporarily pausing the
allocator or capping individual controller outputs. Previously the only way to
write a controller setting while the supervisor was running was to stop it
(killing telemetry). This was blocking the VOC experiment.

**What shipped (`dbfe65d`, `93c2738`, `b578b4c`):**

- `AllocationOverride` class in `charge_allocator.py`: thread-safe, in-memory,
  resets on supervisor restart. `apply()` is called in
  `ChargeAllocationLogger._apply()` just before writes. Manual limits are
  ceilings (allocator evaluates normally; output is clamped). Pause suppresses
  writes while evaluation and logging continue.

- Three API endpoints (in `web_display.py`):
  - `GET /api/v1/control/allocation/status`
  - `POST /api/v1/control/allocation/pause` — `{"paused": true/false}`
  - `POST /api/v1/control/allocation/manual-limit` — `{"controller": N, "limit_a": X}`

  Controller is addressed by integer index (0 = Classic, 1 = EPEver), not brand
  name. Returns `409` when allocation is not enabled.

- `scripts/allocation-override.py`: CLI wrapping the three endpoints. Usage:
  `status`, `pause`, `resume`, `limit N AMPS`, `limit N --clear`.

- Override state is reflected immediately in `GET /api/v1/snapshot` without
  waiting for the next allocation cycle: `SnapshotCache.get_allocation()` merges
  the live `AllocationOverride` state on every read.

- Charge Allocation display group updated in both `terminal_display.py` and
  `api_terminal_display.py`: header shows `(paused)` when allocator is paused;
  per-controller rows show `→ N A manual ceiling` when a ceiling is active.

- 20 new unit tests (10 in `test_charge_allocator.py`, 8 in `test_web_display.py`).
  All 403 tests pass.

## EPEver temperature and SOC register fix

**Problem:** EPEver was reporting battery_temp = 0.0 °C and SOC = None. Front panel showed 25 °C and ~59 %.

**Root cause:** Code was reading `0x3110` (battery temp) and `0x3111` (device temp) from the generic Tracer map. Those registers read 0 on the TEP10425. A separate SOC read at `0x311A` was returning 2053 (>100, clamped to None) because `0x311A` is device temp, not SOC.

**Fix (commit `93c592b`):** Read a 3-register block starting at `0x3118`:
- `0x3118` = battery temp ×100 °C
- `0x3119` = SOC %
- `0x311A` = PCB/device temp ×100 °C

Confirmed live: 2500 = 25.0 °C (matches front panel), 59 = 59 %, 2053 = 20.53 °C.

`decode_telemetry()` signature: removed separate `soc` parameter; SOC now comes from `temperatures[1]`. Regression test added with live-observed values. Documented in `docs/research/epever-tep10425.md`.

## 0x901B — not a MOSFET temperature

Probed holding register `0x901B` following a rumour it holds a Power Component / MOSFET temperature. Read back 6662 = `(26 << 8) | 6` — this is the RTC year/month word (June 2026), the third register of the `0x9019..0x901B` device-time block already documented. No live MOSFET temperature register is accessible on this unit. The only live thermal channels are `0x3118` (battery probe) and `0x311A` (PCB). `0x901E` / `0x901F` are over-temperature protection thresholds (85 °C / 75 °C), not live readings.
