## Classic VOC as irradiance proxy while charging is disabled

Ongoing question: when pack temperature drops below 0 °C and charging is
disabled entirely, what signal tells us whether the sun is strong enough to
justify running the 200 W battery heater? The EPEver coil is open; the Classic
trickles at its floor. Neither output current is informative.

**Investigation:** Pulled historical telemetry correlating `last_voc` (Classic
register 4122) and `pv_voltage` (4116) with power output during Bulk charging.
Filtered to periods with allocator target ≥ 25 A to exclude severely
current-limited samples. Result: 130–132 V `last_voc` is the zone where ≥ 200 W
output becomes likely; 134 V+ is the zone where it is nearly certain.

**Experiment (2026-06-26):** Used the new allocation override API
(`allocation-override.py limit 0 0`) to cap Classic output at 0 A while the
supervisor and telemetry kept running. Observed `last_voc` updating every ~60
seconds and tracking passing clouds in real time (131.4 → 130.6 → 131.4 → 131.2
→ 131.0 → 129.8 over eight minutes). **Conclusion confirmed: `last_voc` is
independent of charge state.** The Classic performs VOC sweeps internally as
part of its MPPT algorithm and records them to register 4122 continuously
regardless of its current-limit register or the BMS charge-enable state.

`pv_voltage` also tracks near-VOC levels whenever Classic output is near zero,
making it a real-time second proxy for the same irradiance signal.

**Proposed heater heuristic** (not yet automated):

1. Pack temperature ≤ 0 °C
2. Current time between sunrise and sunset
3. `pv_voltage` or `last_voc` > 132 V

Documented in `docs/charge-management.md` under "Cold-Weather Operation."

**SQLite ownership incident:** Running `sqlite3` as the `tvetter` user
re-creates the WAL and SHM files with wrong ownership, blocking the `offgrid`
supervisor from writing. Fix: always use `sudo -u offgrid sqlite3 ...` to query
the database interactively. Restarting the supervisor after fixing ownership
(`sudo chown offgrid:offgrid metrics.sqlite-shm metrics.sqlite-wal`) restores
writes and the fallback buffer merges automatically.

## Allocation override API

Built a supervisor-resident control surface for temporarily pausing the
allocator or capping individual controller outputs. Previously the only way to
write a controller setting while the supervisor was running was to stop it
(killing telemetry). This was blocking the VOC experiment.

**What shipped (`dbfe65d`, `93c2738`, `b578b4c`):**

- `AllocationOverride` class in `charge_allocator.py`: thread-safe, in-memory,
  resets on supervisor restart. `apply()` is called in
  `ChargeAllocationLogger._apply()` just before writes. Manual limits are
  ceilings (allocator evaluates normally; output is clamped). Pause suppresses
  writes while evaluation and logging continue.

- Three API endpoints (in `web_display.py`):
  - `GET /api/v1/control/allocation/status`
  - `POST /api/v1/control/allocation/pause` — `{"paused": true/false}`
  - `POST /api/v1/control/allocation/manual-limit` — `{"controller": N, "limit_a": X}`

  Controller is addressed by integer index (0 = Classic, 1 = EPEver), not brand
  name. Returns `409` when allocation is not enabled.

- `scripts/allocation-override.py`: CLI wrapping the three endpoints. Usage:
  `status`, `pause`, `resume`, `limit N AMPS`, `limit N --clear`.

- Override state is reflected immediately in `GET /api/v1/snapshot` without
  waiting for the next allocation cycle: `SnapshotCache.get_allocation()` merges
  the live `AllocationOverride` state on every read.

- Charge Allocation display group updated in both `terminal_display.py` and
  `api_terminal_display.py`: header shows `(paused)` when allocator is paused;
  per-controller rows show `→ N A manual ceiling` when a ceiling is active.

- 20 new unit tests (10 in `test_charge_allocator.py`, 8 in `test_web_display.py`).
  All 403 tests pass.

## Number-based charge controller API surface

User requirement: charge controllers should be addressed canonically by integer
index (0, 1) in all APIs and scripts, not by brand name. Brand names are
permitted in JSON response fields for display purposes, but not as routing
parameters.

**What shipped (`b578b4c`):**

- Three new canonical endpoints in `route_control_request()`:
  - `POST /api/v1/control/charge-controller/charge-settings` — `{"controller": N, ...}`
  - `POST /api/v1/control/charge-controller/charging` — `{"controller": N, "enabled": bool}`
  - `POST /api/v1/control/charge-controller/sync` — `{"source": N, "target": N, ...}`

  Brand-name aliases (`/classic/charge-settings`, `/epever/charge-settings`,
  `/epever/sync-from-classic`, `/epever/charging`) preserved for backward
  compatibility.

- Scripts updated to canonical paths:
  - `epever-boost-step.py` → `/charge-controller/charge-settings` with `"controller": 1`
  - `epever-copy-from-classic.py` → `/charge-controller/sync` and `/charge-controller/charge-settings`
  - `epever-coil.py` → `/charge-controller/charging` with `"controller": 1`

- `charge-controller/voltage` and `allocation/manual-limit` were already
  number-based; no change needed.

- `magnum/charge-settings` left as-is: the Magnum is an inverter/charger
  outside the allocation system and has no controller index.
