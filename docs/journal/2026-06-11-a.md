# 2026-06-11 — EPEver live, Magnum on its own adapter, logging overhaul planned

## EPEver TEP10425 in service

The second charge controller powered up and is now read over Modbus RTU
via the DSD SH-U11H adapter (reassigned from the Magnum), surfaced as
`Charge Controller 1 (Epever)` on all displays. Register map followed the
standard EPEver/Tracer layout. Notable manual findings carried into the
controller doc: native LFP16S profile runs hotter than our practice;
user-define 36-62 V covers conservative setpoints; `CPE=OFF` would kill
comms at night (keep ON); and a native closed-loop BMS mode (BPRO/UBS)
exists but is **not usable as the policy plane** here — the Cubix
publishes a static 58.4 V / 200 A protection envelope (1,487 snapshots,
never modulated), so the supervisor's taper stays the charge authority.
Consolidating both arrays on the EPEver's dual input was considered and
parked: the Classic stays on array 0 for redundancy and nine years of
reliability; the dual input is the Classic-failure contingency.

## Magnum moved to a dedicated KL0823B adapter

Freeing the SH-U11H for the EPEver had mothballed Magnum telemetry. A
KL0823B 2-wire (CH340) adapter now serves the Magnum read-only tap at
`/dev/magnum-rs485`; clean frame decode confirmed (0x73 model byte,
~53.6 V). 2-wire is sufficient because the tap never transmits — but that
is **policy (decision 0002), not a hardware limit**: the adapter is
TX-capable, so the banked inverter-toggle path remains available. The
Inverter/Charger display group, dropped during the mothball, was restored
across web/terminal/API surfaces.

Serial-adapter fleet now cleanly separated, each with a stable udev name:
KL0823B → `/dev/magnum-rs485`, SH-U11H → `/dev/epever-rs485`, FT232R →
`/dev/cubix-rs485` (Waveshare repurposed as spare).

## Logging overhaul planned + SSD proofed (decision 0003)

Reviewed the logging architecture: three overlapping models (JSON-snapshot
blobs as the live store, an empty-but-built flat `metric_samples`
time-series, and redundant CSVs) plus a high-volume access log nothing
reads. Decided (ADR 0003) to consolidate on the **flat EAV time-series**
as canonical — it preserves schema flexibility for new metrics with no
migration, and its content-hashed `sample_id` makes cross-store merge an
idempotent union. R2 export → date-partitioned Parquet; DuckDB as the one
query engine spanning local SQLite + R2 for ad hoc charting on both.

The Samsung 840 EVO was wiped (was Mac/APFS), ext4-formatted, and proofed
at `/mnt/ssd-test` on the Apricorn BOT bridge via the powered hub:
36.8/36.9 MB/s fresh write/read (USB 2.0 ceiling), WAL inserts trivial.
The 8.8 MB/s first read was the 840 EVO aged-cell slowdown on old data,
gone after reformat. Operator decision: log integrity is out of scope for
a long time, so build the production-like store on the SSD **now** rather
than waiting for the dedicated adapter — made safe by the rule that
logging is best-effort and strictly isolated from the supervisor.
Supersedes the SD-durability plan item.

A correction worth remembering: the brownout risk that wedges the CAN
adapter is about the Pi's *shared USB rail*, not bus-powered adapters per
se. On the powered hub the SSD draws from the hub PSU, so prototyping is
fine. (The Pi 3B+ runs all USB ports + onboard ethernet behind one
internal hub on a single 480 Mbps link — a real ~35-40 MB/s ceiling, but
irrelevant to a log workload.)

## Also today

- **EPEver Solar Guardian sniff session:** captured the Windows Solar
  Guardian Modbus RTU behavior through the SH-U11H while passively sniffing
  from the Pi. Durable findings are now in the EPEver research note:
  charge-control voltage writes require Battery Type = `User`; Solar
  Guardian uses function `0x10` writes; the whole voltage block is
  `0x9007..0x9012`; battery max charge current/taper is `0x9013`
  centiamps; and Home/status polling covers `0x31xx`, `0x32xx`, `0x33xx`,
  and `0x34xx` input-register blocks. No true charger enable/disable
  register was seen.
- **Away-mode Starlink forwarding** design note: keep the inverter off
  while the cabin is unoccupied, wake it periodically to power Starlink
  (sole connected AC load) for a telemetry export, then off. The real win
  is eliminating the inverter's ~25-50 W idle draw (~15 Ah/day), not the
  forwarding cost. This is the concrete application for the banked
  inverter-toggle capability (decision 0002 addendum). Hard dependency:
  the Pi is DC-powered, so it survives inverter-off to wake it again —
  never move it to inverter AC. DC-powering Starlink was preferred but
  rejected on buck-boost BOM (odd regulated voltage vs the 44.8-58.4 V bus
  swing).
- **Mollom battery breaker** arrived: it is **polarized**, which is wrong
  for the charge-controller battery leg where charging and fault currents
  flow opposite directions. Recommended replacements: hydraulic-magnetic
  (Carling/ETA), MidNite MNEDC (bidirectional, ecosystem-native), or
  Class T fuse + disconnect. Also arrived as 125 VDC, not the 250 ordered
  (still ample). PV-side breakers may be polarized; battery-leg must be
  bidirectional — recorded as a principle.
- **Weme bus-powered bench hub** added for keyboard/mouse overflow; its
  built-in RTL8153 NIC deauthorized via udev to cut USB draw.
- **Parts-box reconciliation:** spare KL0823B logged (with a
  cell-monitoring-tap feasibility note — adapter is fine, but protocol is
  undecoded and it would be an active transmit interaction); YL-128
  modules confirmed full-duplex RS422 by pinout (Y/Z driver + A/B
  receiver), no current role since all our buses are 2-wire RS485.
