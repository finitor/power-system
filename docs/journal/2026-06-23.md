## Magnum RS485 glitch rate + stale threshold

Picked up where the previous session left off mid-implementation.

**Problem:** Magnum RS485 read failures were generating frequent "read failed"
warnings because the stale threshold defaulted to `interval_s × 4 = 20 s`. Also
wanted visibility into the *rate* of these errors to track the trend over time.

**What shipped (`71e9667`):**

- `readers.py` — added a 720-entry ring buffer (`_poll_history`) recording
  `(monotonic_timestamp, success)` for every poll attempt; added
  `error_rate_pct(window_s=300)` method that returns the fraction of failed
  polls in the last N seconds as a percentage (or `None` before any polls run).
- `config.py` — `MAGNUM_STALE_AFTER_SECONDS` env var (default 60 s); wired
  through `DisplayConfig`.
- `supervisor.py` — `reader_error_rates: dict[str, float | None]` field on
  `SupervisorSnapshot`; `_reader_error_rates()` method; `start_readers()` now
  accepts `magnum_stale_after_s`.
- `cli/supervisor_display.py` — `--magnum-stale-after-seconds` CLI arg; passes
  value to `start_readers()`.
- `terminal_display.py` — replaced static Protection row (GFP/Arc — settings
  that never change) with "RS485 Glitches: Magnum X.X% (5 min)"; row is hidden
  until the first Magnum poll runs.
- `api_terminal_display.py` — same row, placed after the inverter section
  (Magnum is the inverter, not a charge controller); Protection row removed.
- `web_display.py` — `reader_error_rates` included in the top-level API payload.
- Tests updated: replaced `test_protection_row_renders_below_production_today`
  with two new tests for the RS485 Glitches row; added `error_rate_pct()` stub
  to `FakeReader` in `test_readers.py`.

**Metric nuance** (documented in `error_rate_pct` docstring, `2057d28`): this is
a poll-failure *rate*, not a glitch count. A single dropped frame and a sustained
5-minute outage both contribute equally per sample. Fine for trend-watching; if
we ever want to distinguish transient noise from sustained failures, count
distinct error runs (consecutive-failure spans) instead.

## SD card swap SSH post-mortem

After deploying, SSH to `blueberry.local` failed. Root-caused three separate
issues:

1. **`authorized_keys` clobbered by restore** (`d806317`): step 6 of the card
   build runbook extracted `~/.ssh/` from the backup bundle, overwriting the
   `authorized_keys` that Raspberry Pi Imager had just injected. Fixed: save
   Imager's `authorized_keys` before extracting, grep-merge it back after.

2. **Mac SSH key not persistent** (`d806317`): no `~/.ssh/config` existed on the
   Mac, so the key fell out of the agent after session end. Fixed in the runbook
   (step 3): create `~/.ssh/config` with `AddKeysToAgent yes` / `UseKeychain yes`
   and run `ssh-add --apple-use-keychain`. Applied to this machine now.

3. **Wrong username** (`8bb71ff`): tried `pi@blueberry.local`; correct user is
   the one created in Pi Imager. Step 4 now says `ssh <user>@blueberry.local`
   explicitly.

4. **PII cleanup** (`adb4205`): `tvetter` username had leaked into two runbooks.
   Replaced with `<user>` placeholder throughout, consistent with the existing
   convention in `pi-boot-card-build.md`.

## Network reachability monitoring

Added `NetworkMonitor` and a full set of display/telemetry behaviors for LAN
and WAN connectivity. Motivation: the Classic charge controller communicates
over Modbus TCP; if the router is down, reads fail and errors surface as
device-level noise rather than a single root-cause condition. WAN (Starlink) is
expected to be offline for long periods by design.

**What shipped (`68de0a2`, `b641967`, `c6fcfd8`–`85afa72`):**

- `network_monitor.py` — `NetworkMonitor`: daemon thread, ping gateway for LAN
  (`-c 1 -W 1`), TCP connect to 8.8.8.8:53 for WAN, 30 s interval,
  lock-protected `bool | None` properties. Configured via `LAN_GATEWAY` /
  `LAN_CHECK_INTERVAL_SECONDS` env vars (defaults: 192.168.0.1 / 30 s).
- `WanReachabilityTracker`: stateful observer that emits a `TelemetryEvent`
  (`source="network"`, event `"wan_up"` / `"wan_down"`) on each transition.
  Per-tick sampling would be noise for a WAN that's down for hours — only
  transitions are logged.
- `supervisor.py` — `SupervisorSnapshot` gains `lan_reachable` / `wan_reachable`
  fields. LAN unreachable injects a `StatusConditionCandidate("network.lan_unreachable",
  severity=ERROR)`. Classic Modbus read errors are suppressed when LAN is down
  (the LAN condition is the root cause; per-device noise would be redundant).
  Classic's **cached value is also cleared immediately** on LAN down — the reader
  grace window exists for RS485/CAN glitches, not for definitive TCP failures.
- `metrics.py` — `network.lan_reachable` sample emitted every tick (0.0/1.0);
  WAN logged as events only (see WanReachabilityTracker above).
- `snapshot_status_annotations()` — single source of truth for display-level
  annotations, consumed by all renderers. Emits `["LAN offline"]` when LAN is
  down, `["WAN offline"]` when LAN is up but WAN is down. LAN supersedes WAN
  because WAN goes down as a side effect of LAN outage.
- All displays updated: terminal, api_terminal_display, Kindle HTML, browser HTML,
  weather pages. `snapshot_severity_text()` composes the standard parenthetical
  form (`"OK (WAN offline)"`). Weather pages pass annotations through separately
  so the Kindle header can say "OFFLINE as of HH:MM TZ" without the status shape
  of the power screens.
- `_solar_api_payload()` — now injects a stub entry (`"status": "unreachable"`)
  for any configured-but-offline device, preserving its heading at the correct
  index. All three renderers check the stub flag and render `"— UNREACHABLE"` in
  the heading with no data rows. Previously the section vanished entirely.

**Verified by two deliberate outage tests:**

- *LAN outage (router off ~17 min):* telemetry confirmed `lan_reachable` → 0.0
  at the moment of outage; `supervisor.error_count` stayed 0.0 throughout (Classic
  errors correctly suppressed). WAN went down simultaneously (router provides WAN).
- *LAN outage (router off ~7 min):* verified Classic section switches to
  UNREACHABLE at the same time status shows "LAN offline" (no stale-value window),
  and annotation correctly shows "LAN offline" rather than "WAN offline".
- *WAN-only transitions (Starlink blips):* three wan_down / wan_up pairs during
  the same test window, tracked correctly as events, LAN stayed up throughout.
