## Magnum RS485 glitch rate + stale threshold

Picked up where the previous session left off mid-implementation.

**Problem:** Magnum RS485 read failures were generating frequent "read failed"
warnings because the stale threshold defaulted to `interval_s × 4 = 20 s`. Also
wanted visibility into the *rate* of these errors to track the trend over time.

**What shipped (`71e9667`):**

- `readers.py` — added a 720-entry ring buffer (`_poll_history`) recording
  `(monotonic_timestamp, success)` for every poll attempt; added
  `error_rate_pct(window_s=300)` method that returns the fraction of failed
  polls in the last N seconds as a percentage (or `None` before any polls run).
- `config.py` — `MAGNUM_STALE_AFTER_SECONDS` env var (default 60 s); wired
  through `DisplayConfig`.
- `supervisor.py` — `reader_error_rates: dict[str, float | None]` field on
  `SupervisorSnapshot`; `_reader_error_rates()` method; `start_readers()` now
  accepts `magnum_stale_after_s`.
- `cli/supervisor_display.py` — `--magnum-stale-after-seconds` CLI arg; passes
  value to `start_readers()`.
- `terminal_display.py` — replaced static Protection row (GFP/Arc — settings
  that never change) with "RS485 Glitches: Magnum X.X% (5 min)"; row is hidden
  until the first Magnum poll runs.
- `api_terminal_display.py` — same row, placed after the inverter section
  (Magnum is the inverter, not a charge controller); Protection row removed.
- `web_display.py` — `reader_error_rates` included in the top-level API payload.
- Tests updated: replaced `test_protection_row_renders_below_production_today`
  with two new tests for the RS485 Glitches row; added `error_rate_pct()` stub
  to `FakeReader` in `test_readers.py`.

**Metric nuance** (documented in `error_rate_pct` docstring, `2057d28`): this is
a poll-failure *rate*, not a glitch count. A single dropped frame and a sustained
5-minute outage both contribute equally per sample. Fine for trend-watching; if
we ever want to distinguish transient noise from sustained failures, count
distinct error runs (consecutive-failure spans) instead.

## SD card swap SSH post-mortem

After deploying, SSH to `blueberry.local` failed. Root-caused three separate
issues:

1. **`authorized_keys` clobbered by restore** (`d806317`): step 6 of the card
   build runbook extracted `~/.ssh/` from the backup bundle, overwriting the
   `authorized_keys` that Raspberry Pi Imager had just injected. Fixed: save
   Imager's `authorized_keys` before extracting, grep-merge it back after.

2. **Mac SSH key not persistent** (`d806317`): no `~/.ssh/config` existed on the
   Mac, so the key fell out of the agent after session end. Fixed in the runbook
   (step 3): create `~/.ssh/config` with `AddKeysToAgent yes` / `UseKeychain yes`
   and run `ssh-add --apple-use-keychain`. Applied to this machine now.

3. **Wrong username** (`8bb71ff`): tried `pi@blueberry.local`; correct user is
   the one created in Pi Imager. Step 4 now says `ssh <user>@blueberry.local`
   explicitly.

4. **PII cleanup** (`adb4205`): `tvetter` username had leaked into two runbooks.
   Replaced with `<user>` placeholder throughout, consistent with the existing
   convention in `pi-boot-card-build.md`.
