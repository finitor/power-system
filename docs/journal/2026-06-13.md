# 2026-06-13 — 64-bit dry-run card prep

## Backup completeness before salvaged-card rehearsal

A 32 GB microSD salvaged from another Pi is acceptable for a 64-bit migration
dry run: the current root filesystem uses about 7.3 GB, and `/srv/telemetry`
is on the external Samsung SSD 840 EVO rather than the boot card. It is not
the desired final medium, but it is enough to rehearse the image, restore, and
health-check path while leaving the current 64 GB Samsung boot card untouched
as physical rollback.

Tightened the migration backup/restore coverage before doing the dry run:

- Back up `/etc/fstab`, `/etc/hostname`, `/etc/hosts`, relevant cloud-init host
  config/template files, sudoers snippets, local sshd config, NetworkManager,
  systemd-networkd, wpa_supplicant, and `/boot/firmware/{config,cmdline}.txt`.
- Restore keeps the full old `fstab`, `config.txt`, `cmdline.txt`, and
  sudoers snippets only as reference files on the new image. It does **not**
  overwrite the fresh image's boot/root fstab or cmdline, because those carry
  card-specific root identity; it also does not automatically restore temporary
  privilege files.
- Restore extracts just the `/srv/telemetry` line from the old fstab and
  appends it if the new image does not already have that mount. Current live
  line is the external SSD UUID mounted at `/srv/telemetry` with
  `nofail,x-systemd.device-timeout=10`.

Next step is to deploy these backup changes to the live 32-bit Pi, create a
fresh migration backup, verify that the archive contains the new completeness
items, and only then flash the 32 GB dry-run card.

## 64-bit Lite dry run completed

The salvaged 32 GB microSD was flashed with Raspberry Pi OS Lite 64-bit and is
now running in service as `blueberry`. The former 64 GB Samsung card was left
untouched as the physical rollback.

Final verified state:

- Host reachable at `blueberry.local` with normal SSH known-host handling.
- Architecture is `aarch64`; OS is Debian GNU/Linux 13/trixie.
- Repo deployed at Git commit `4db22d5`.
- Reboot survived and `/srv/telemetry` remounted from the external Samsung SSD.
- `offgrid-supervisor`, `offgrid-console`, `nginx`,
  `offgrid-can-watchdog.timer`, and `offgrid-metrics-export.timer` are enabled
  and active.
- Supervisor `/healthz` returns `ok`; the Kindle nginx path returns OK.
- Full health check is green, including battery CAN, Classic, and EPEver.
- The temporary migration sudoers file was removed; `sudo -n true` now fails
  as expected.

Migration fixes made during the dry run:

- Restore no longer tries to preserve ownership into `/boot/firmware`, which is
  a vfat filesystem on the fresh image.
- Restore skips nginx validation before nginx is installed.
- Deploy enables the nginx site and removes the default site.
- Deploy enables the supervisor services after installing them.
- EPEver is pinned to the physical USB path
  `/dev/serial/by-path/platform-3f980000.usb-usb-0:1.3.3:1.0-port0`, because
  the two serial-less CH340 adapters make `/dev/epever-rs485` ambiguous.
- The local Mac tmux watcher recipe was added to the migration runbook for
  long installs and future rebuilds.
