# 2026-06-15 — EPever charge cutoff: BMS/CAN dead-ends, and the on/off coil

The motivating problem: the supervisor's Modbus charge taper bottoms out at
1 A (`0x9013` BAT max current floors at 1 A), so it is a taper, not a true
charge stop. Today's session hunted for a real "stop charging" primitive on
the EPever TEP10425, went deep into the BMS and CAN paths, found they are
dead ends, and then found the answer hiding in plain sight on the COM port.

## CAN as a BMS path — conclusively ruled out

Two newly-added EPever docs in Dropbox settled the transport question. The
**BMS Communication Protocols & Fixed ID** table (V1.5) lists all 35 protocols
with a type column — **every one is RS485** (Modbus / Pylon "Telecom" /
User-Define); **none are CAN**. Pylon is protocol **21 = RS485**
low-voltage-V3.5, on port-9 pins 3/6. So the controller's BMS/closed-loop
plane is exclusively RS485. That alone explains the 2026-06-12 silent-RS485
result was the *right* pins after all — the puzzle was never CAN.

We sniffed port-9 CAN anyway, for completeness. The EPever emits exactly one
frame, arbitration ID `0x17343732` (PGN 0x33400, **EDP=1** → proprietary, not
RV-C/J1939), a 5-part multiplexed status broadcast carrying its *own* data
(battery voltage, the 1200 A parallel-max ceiling) — confirmed by
cross-checking against its Modbus registers. We then bridged the Cubix's
Pylon CAN onto port 9 alongside the EPever: the sniffer decoded both cleanly
(Cubix SOC 81%, CVL 58.4 V, CCL 200 A), but the **EPever's Modbus side was
byte-identical to the no-battery baseline** — no SOC, no BMS-fed limits, no
status change. The controller does not ingest Pylon-over-CAN, as the protocol
table predicts. (And the Cubix's published envelope is the static 58.4 V /
200 A protection max with "charge enable" at 81% SOC, reaffirming that UBS-as-
policy was never viable here regardless.)

## CAN-write reverse engineering — no usable path

Pushed on the proprietary CAN for a *write* primitive since we were wired for
it. Active injection (J1939 PGN requests, a frame addressed to the controller
on its own page, an echo of its broadcast ID) produced **no response and no
register change** — except a one-time `0x9041` read of `768` that **did not
reproduce** across two exact replays and both isolations, so it was a
transient artifact, not a control effect. A cleanly-addressed inbound frame
changed nothing. Conclusion: no usable blind CAN-write; the broadcast is
proprietary and undocumented, so the only way further on CAN would be an
EPever spec request (earmarked, low priority now). Controller config snapshot
verified intact before/after.

## The find: coil `0x0000` "Charging device on/off"

The real charge enable/disable is a **coil**, not a holding register — which
is exactly why every prior sniff (Solar Guardian, our own work) missed it:
all our control had been holding-register writes (fn `0x10`), and we had
never read the coil table (fn `0x01`/`0x05`), a separate address space. The
EPever B-series coil map gives **coil `0x0000` = Charging device on/off**
(1=on, 0=off). Verified over port 8 (the COM port we already own):
wrote 0 → read 0 → wrote 1 → read 1, reversible, write accepted via fn `0x05`.

This is the true 0 A stop, on the link the supervisor already drives — beating
every other candidate (BMS emulation needs port-9 rewire + polling; CAN-write
doesn't exist; a DC-rated PV contactor is a purchase we don't have parts for —
the on-hand relay/opto board are not rated for the array Voc). It corrects the
old "no charger enable/disable register" note in the research doc.

## The rest of the port-8 charge-control surface

Mapped the TEP-specific `0x9000` block (the B-series numbering does **not**
apply there — e.g. `0x9004` is screen-backlight time on the TEP, not charging-
limit voltage; verified live). The useful charge knobs: voltage block
`0x9007-0x9012` (boost/float/equalize, bounded by the `0x9008` CV ceiling),
`0x9013` current taper, and the **stage-duration timers** `0x9014`
(boost/absorption hold, ~"Bulk Charging Time" in EPever's loose labeling) and
`0x9015` (equalize) — both 120 min currently; for LiFePO4 these are longer
than needed and worth trimming, with behavioral confirmation under PV.

`0x9039`/`0x903A` SOC-based full-charge cutoff exists but is **deprioritized**:
it would need a trustworthy SOC on the controller (a BMS link we don't have),
and more to the point the supervisor already owns *both* ends — it reads SOC
from the Cubix CAN and can drive coil `0x0000` / `0x9013` / the voltage block
directly over port 8. SOC cutoff belongs in software, not delegated to the
controller. Voltage-flooring (charge targets below live Vbat) remains a no-
new-hardware fallback stop, now superseded by the coil.

## Bench/ops housekeeping

- **GND is optional on the Cubix CAN link**: removed it at the adapter and
  telemetry held over the 2-wire pair across a 100 ft patch run (isolated
  SH-C31G). Mattered for cable reuse — port-9 pins 3/6 are RS485, so the
  Cubix cable's GND wire would otherwise land on an RS485 pin.
- **One CH340 at a time, going forward.** The two identical KL0823B adapters
  caused repeated udev-symlink identity confusion (`/dev/epever-rs485` kept
  resolving to the wrong tap). Removed the spare from the hub and adopted a
  standing rule never to run two at once. That let us **revert the supervisor's
  by-path pin back to the `/dev/epever-rs485` udev symlink** and drop the stale
  collision comment — simpler and robust to USB-port changes.
- Supervisor + CAN watchdog restored and verified: EPever read via the clean
  symlink, Cubix CAN flowing (SOC 88%, 54.61 V), both controllers in the
  snapshot, `can0` listen-only 500k healthy. Controller config left as-found
  (charging on, `BPRO=21`, `UBS=1`, setpoints untouched).

Findings captured in `../research/epever-tep10425.md` (port-8 control surface,
coil `0x0000`, charge-knob map, CAN conclusions) and `../wiring.md`.
