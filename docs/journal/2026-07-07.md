# 2026-07-07

## USB RS485 rebinding after hub move

Moved the two serial-less CH340 RS485 adapters onto the powered USB hub and
re-keyed their udev identities by the new physical paths:

| Device | Symlink | Path | Verification |
|---|---|---|---|
| Magnum network tap | `/dev/magnum-rs485` | `platform-3f980000.usb-usb-0:1.3.2:1.0` | Magnum-only supervisor read decoded inverter status |
| EPEver COM adapter | `/dev/epever-rs485` | `platform-3f980000.usb-usb-0:1.3.3:1.0` | `scripts/epever-probe.py --device /dev/ttyUSB1` read Modbus registers at 115200 baud |

Before rebinding, the installed rules still expected Magnum on `1.2` and
EPEver on `1.5.3`, so neither canonical symlink existed after the move and the
supervisor logged repeated `/dev/epever-rs485` missing errors. Reloaded udev,
triggered tty devices, and restarted `offgrid-supervisor`; the API returned
status OK with Classic, EPEver, Magnum, and battery telemetry present.

The CH340 adapters still share VID:PID and generic serial
`1a86_USB2.0-Serial`, so identity continues to follow hub port, not adapter
body. Keep physical labels on the hub ports and adapter leads.

## Telemetry SSD remount after USB re-enumeration

The USB move also took the telemetry SSD offline. The kernel reported device
offline writes and ext4 journal abort on `sda1`; systemd unmounted
`/srv/telemetry` at 11:21. The disk reappeared on the new USB path, but the
mount unit did not restart on its own. While unmounted, the supervisor correctly
wrote to `/var/lib/offgrid/metrics-fallback.sqlite`; however, that fresh
fallback store lacked the local-midnight EPEver lifetime-energy baseline, so the
display reported "midnight cumulative energy was not logged."

Manually starting `srv-telemetry.mount` recovered the ext4 journal, remounted
the SSD, restored the EPEver daily-energy baseline from the primary store, and
merged the fallback gap back into the primary database.

Added a udev/systemd hook keyed to the telemetry SSD filesystem UUID
`8e8a4fee-51ec-43b2-9b8b-b0a51cecf7e0`: when the block device appears or
changes, udev tags it for systemd and requests `srv-telemetry.mount`. The mount
unit is still the fstab-generated unit, so fsck/recovery remains systemd-owned.
