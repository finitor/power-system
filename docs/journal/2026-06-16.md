# 2026-06-16 — Parquet exporter on 64-bit, health degraded-vs-down, Magnum back on the SH-U11H

Three threads today, each building on the last: the telemetry exporter finally
took the Parquet serializer the 64-bit migration unblocked; the health
endpoints learned to tell *degraded* from *down*; and chasing why one health
check looked wrong led into the RS485 adapter wiring and brought the Magnum tap
back online.

## Telemetry: NDJSON → Parquet, and a clean bucket

The Pi has been on 64-bit Raspberry Pi OS Lite (Debian 13/trixie, `aarch64`,
Python 3.13.5) since 2026-06-13, which lifted the armv7l wheel constraint that
forced gzipped NDJSON in the first place. So the exporter swap that
[decision 0003](../decisions/0003-telemetry-storage-model.md) always predicted
is done: `build_export_batch` (`offgrid_power/r2_export.py`) now writes
**snappy Parquet via pyarrow** (`pyarrow==24.0.0` added to deps). Object suffix
`.parquet`, content type `application/vnd.apache.parquet`, same hive layout.
Per-table schemas, since each batch is single-table: samples typed with `tags`
as `map<string,string>`; events keep `detail` as a JSON string (heterogeneous
across event types, so no fixed struct). DuckDB stays the Mac-side reader —
`read_parquet` now instead of `read_json`. Commit `67aa988`.

Then the **bucket reset clean**. The operator wanted no mixed-format archive,
so all 103 old `.ndjson.gz` objects were deleted from B2 (`magpie-metrics`,
us-east-005) — including two pre-2026-06-12 *flat-layout* stragglers that
predated the current `date=`-partitioned scheme and were the only surviving
copy of that early data (acceptable: it was the pre-flat-store data the operator
had already wiped locally on 06-12). No backfill; the unexported rows re-drained
as Parquet, so the bucket is now uniformly `.parquet`. Parquet+snappy is
markedly tighter — 85k rows in 6.25 MiB vs the old NDJSON's 22.7 MiB.

Records corrected along the way: the deployment runs on **Backblaze B2**, not
Cloudflare R2 (the `R2_*`/`offgrid-r2-export` names are a provider-agnostic
legacy — the client accepts `R2_`/`B2_`/`S3_`). Fixed the living docs that
implied R2-as-store, marked the export-timer "disabled" action done, amended
ADR 0003 to note Parquet is now live, and switched the store-and-forward
reference to Parquet/`read_parquet`. Commit `d0799e3`.

## Health endpoints: degraded is not down

The `/healthz` 503 we kept seeing wasn't the supervisor being broken — it was
**one offline charge controller**. Both `/healthz` and `/api/v1/health` derived
their HTTP status from a single boolean (`snapshot.ok`), and *any* device read
error forced `ok=False` → 503. That conflates "a sensor is offline" with "the
supervisor is wedged," which is wrong because the remediation differs:
restarting the supervisor cannot bring back an offline EPEver. A health check
should fail only when its consumer's reaction to failure would actually help
(the k8s liveness/readiness split; IETF `draft-inadarei-api-health-check`).

The fix, in three commits:

- **`29de711` — degraded vs down.** A device read failure is now `WARNING`
  (degraded), not `ERROR`; `ERROR` is reserved for critical analyzed conditions
  (battery overvoltage). `ok` means "not in a hard-error state" (a `WARNING` is
  still `ok`). `/healthz` became a pure **liveness** probe — `200` whenever a
  snapshot is produced, regardless of device errors; the "can't produce a
  snapshot at all" case still returns `503` upstream in the server.
  `/api/v1/health` maps severity to HTTP (`OK`/`WARNING` → 200, `ERROR` → 503)
  and gained a per-device `checks` object plus `conditions`; `schema_version` 2.
- **`8396fd5` — reason classification.** Each check carries a `reason` derived
  *only from the observed signature*, never an inferred cause: `transport_absent`
  (`Could not open …`), `no_response` (port open, device silent / Modbus
  timeout), `no_data`, `unknown`. The point: report what was observed — a Modbus
  no-response can't distinguish "powered off" from "cable out," so we don't
  claim either.
- **`a6c1e20` — `disabled`.** Magnum read `offline`/`no_data` despite there
  being no adapter, which is misleading ("no data" implies a read was tried).
  The snapshot now records `disabled_devices` (adapters with no client
  configured), so an unconfigured device reads `disabled`, distinct from
  `offline` (configured, silent) and `error` (read failed).

## Interfaces: Magnum back online, EPEver node collision fixed

Un-parking the Magnum tap surfaced a real udev problem. Two `SYMLINK` rules
both produced `/dev/epever-rs485` — one keyed on the EPEver's CH340
(`1a86:7523`) and a **stale** one keyed on the SH-U11H (`067b:23a3`, left over
from when the EPEver briefly used that adapter). Plugging the SH-U11H in to host
Magnum hijacked `/dev/epever-rs485` (it resolved to the SH-U11H), pointing the
supervisor's EPEver reads at the wrong adapter — a strong candidate for the
EPEver `no_response` we'd been seeing.

Considered swapping roles (EPEver→SH-U11H, Magnum→CH340) but kept **Magnum on
the SH-U11H**, for two reasons: it avoids rewiring the already-connected EPEver,
and — the real one — the Magnum tap is a **passive mid-bus listener**. The
inverter and the ME-RC50 are the bus endpoints and own termination; the Pi must
not add a third terminator. The SH-U11H has switchable termination (`120R T`/
`120R R` jumpers, left unpopulated), whereas cheap 2-wire CH340 adapters often
carry a fixed 120Ω. So SH-U11H→Magnum / CH340→EPEver is the correct pairing.

Resolution (`8f98684`): the SH-U11H rule now points at **`magnum-rs485`**, keyed
on its unique serial `DZBSb11CN12` (the CH340 has none); the CH340 stays the
sole `epever-rs485`. Nodes are now unambiguous — `epever-rs485` → `ttyUSB0`
(CH340), `magnum-rs485` → `ttyUSB1` (SH-U11H).

A code gap had to close first (`3af9ba5`): `MagnumClient.read()` swallowed every
exception and returned `None`, so an unplugged Magnum adapter could never
surface as `transport_absent` the way the EPEver does (it raises
`ConnectionError`). `read()` now raises `Could not open …` when the serial node
is absent; failures *after* a successful open stay best-effort `None` (a silent
bus is no-data, not an adapter fault).

Enabled with `MAGNUM_DEVICE=/dev/magnum-rs485` in `/etc/offgrid-power.env`
(empty had it `disabled`), supervisor restarted. Breakout wiring per
[wiring.md](../wiring.md): RJ45 pin 6 → adapter A/D+, pin 3 → adapter B/D-,
pins 4 (+14 V) and 5 (GND) left off — **A/B correct on the first try, no swap**.

**Verification.** Magnum decodes sane telemetry: Inverting, **53.6 V DC** /
4 A / 214 W, AC out **119 V / 60 Hz**, fault NONE, temps nominal — correct ×4
48 V scaling, so packet identification (byte 14 = 0x73) is right. The operator
momentarily powered the EPEver back on and confirmed it reappears in the
supervisor display, validating the node remapping; it's otherwise left off and
now reports `error`/`no_response` honestly through its own CH340. (Also clarified
in passing: the CAN adapter is gs_usb/SocketCAN `can0`, a netdev — it has no tty.)

Records updated: `wiring.md` (Magnum line + `RS485 0`/`RS485 1` adapter labels,
commits `b653830`/`714397d`), `supervisor-api.md` (the health contract), and
project memory (the Magnum/EPEver adapter assignment, previously inverted).

# Afternoon — solar array 1 dry-run, and the EPEver register reckoning

The operator dry-ran solar array 1 through the EPEver. That single act surfaced
a cascade of issues — the controller had never actually charged before, so a
lot of code paths met live data for the first time.

## Array 1 online; the EPEver carries the bus

PV came up at ~167 V (well under the 250 V cold Voc). With the bank at 89% and
the Classic holding absorption at ~55 V, the EPEver sat at 0 A / "Resting" —
correct, not a fault: it regulates to voltage (boost 54.40 / float 54.10) and
the bus was already *above* its setpoints, so the higher-regulating controller
(the Classic) owns the charge. To watch a handoff, we tapered the Classic
(absorb/float → 53.0/52.9 V, `--no-persist`, restore captured first) to cede
the bus. The EPEver picked up as the bus fell through ~54.4 V and ramped in via
a gentle soft-start, holding the bus at its own boost setpoint — a clean,
stable handoff, no faults. The Classic is **left tapered on purpose** as a
forcing function to keep surfacing multi-source issues.

## The EPEver register reckoning

The handoff exposed a phantom: the EPEver reported "Resting" while demonstrably
charging. Root cause — charging status is at **`0x3202`, not the generic
`0x3201`** (which reads a flat zero); the bit decode was already right, only the
source register was wrong (`8ae7338`). Pulling that thread through the rest of
the block: the energy counters are **big-endian by word**, generated-today at
`0x330C/0x330D` (`e0fa780`) and the monotonic lifetime total at `0x3310/0x3311`
(`ade07f2`); and the **RTC was mis-set to 2024-10-06** — the crystal keeps good
time but the value was wrong (likely a dead backup). We set it to local time,
and the date jump promptly reset the today/month buckets, confirming they're
RTC-driven. Full detail in
[research/epever-tep10425.md](../research/epever-tep10425.md) "Live register
corrections (2026-06-16)".

## Coil control surface, now in code (and one no-op)

Built the coil-write capability that had been documented-but-absent since
2026-06-15: `EpeverClient.set_charging()` (coil `0x0000`),
`clear_generation_statistics()` (coil `0x000E`), and a guarded
`scripts/epever-coil.py` (`3c726ff`). **Charge on/off verified under live PV** —
drove output 4 A → 0.00 A and back. This is the real emergency charge-stop the
1 A current-taper floor can't give. The **clear coil `0x000E` is a no-op on the
TEP** (byte-identical energy block before/after a pulse) — the panel's CAE maps
elsewhere. It doesn't matter, because of the reframe below.

## Load math: sum all sources, and reframe to autonomy

The instantaneous load estimate assumed a single charge source
(`load = classic_out − battery_net`). With the EPEver contributing, its output
was omitted from charge-in while its share of the battery gain still landed in
the BMS net — so load read **0 W when it was really ~256 W**, and "today"
cumulative went **−6 Ah**. Fixed instantaneous to sum every charge source
(`fd52333`), with the Magnum documented as a third source *only when charging*
(while inverting its draw is already in the BMS net and cancels; its DC-amp sign
is inverted vs the controllers).

The cumulative "today" has the same single-source bug — but rather than patch
it, we reframed. The real metric is **autonomy** (time-to-empty =
SOC×capacity ÷ rolling load); daily-Ah was only ever a means to it. The robust
path is differencing each device's **monotonic battery-side lifetime energy**
over a trailing window: the Classic's `lifetime_energy_kwh` is already there,
the EPEver's `0x3310/0x3311` is now logged, and the Magnum (no counter) would
integrate `dc_power_w`, charger-on only. This sidesteps the RTC/reset problem
entirely — you never clear, you subtract two snapshots — which is also why the
dead `0x000E` clear coil is moot.

## Display: cc1 mirrors cc0

The EPEver charge-controller group now shows "Production Today" (its daily kWh,
exposed under the shared `daily_energy_kwh` key) and drops the static "Rated"
line — a producer-only change; the renderers stayed vendor-agnostic (`1d10d97`).
This puts the EPEver's daily figure on the wall display so we can watch it
across the midnight boundary and validate the RTC-anchored reset.

## Magnum intermittency (watching, not yet root-caused)

The Magnum tap (online since this morning) is logging frequent "no valid
inverter packet seen in 10 cycles" — ~5% of polls, last-good preserved, so it's
WARNING-flap not data loss. It reads as new today; leading hypothesis is EPEver
switching noise coupling into the passive RS485 tap now that array 1 is actively
charging. Discriminator for next time: whether the miss-rate falls as the EPEver
tapers in the evening.
