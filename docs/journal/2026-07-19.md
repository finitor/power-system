# 2026-07-19

## Telemetry SQLite sidecar ownership incident

The primary metrics database stopped advancing at 2026-07-18 14:14 EDT. The
database itself remained owned by `offgrid`, but an operator-side writable
SQLite open created `metrics.sqlite-wal` and `metrics.sqlite-shm` as
`tvetter:tvetter` mode 0644. The unprivileged `offgrid` supervisor could read
the database but could not update the sidecars, producing `attempt to write a
readonly database` on every durable tick.

The existing store-and-forward path worked: the supervisor buffered roughly
201,000 scalar samples in `/var/lib/offgrid/metrics-fallback.sqlite` from
2026-07-18 14:15 onward. This was not a telemetry-loss event; it was a silent
primary-store degradation that the normal health response failed to expose.

Safeguards added:

- recorder health tracks the active store, last write/primary-write times,
  fallback start, and the observed SQLite error;
- the display status, `/api/v1/health`, and `/api/v1/snapshot` expose fallback
  or total-write failure as a non-rebooting `WARNING`;
- diagnostics show fallback size/time range, while deploy and the full health
  check require the primary telemetry check to be `ok`;
- the telemetry directories are setgid with inherited group-write ACLs so
  operator-created SQLite sidecars remain writable by `offgrid`;
- service preflight continues to repair ownership recursively, after which the
  recorder automatically merges the fallback into the primary.

Ad-hoc queries should still use SQLite `mode=ro`; intentional writes should run
as `sudo -u offgrid`.
