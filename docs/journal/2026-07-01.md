# 2026-07-01

## Magnum CH340 moved off the powered hub

For the hub-bypass trial, the Magnum RS485 CH340 adapter was moved from the
Waveshare powered hub to a direct Raspberry Pi USB port. Re-enumeration showed:

- Magnum CH340: `/dev/ttyUSB0`, `1a86:7523`, `ID_REVISION=0254`,
  `ID_PATH=platform-3f980000.usb-usb-0:1.2:1.0`
- EPEver CH340: `/dev/ttyUSB1`, `1a86:7523`, `ID_REVISION=0263`,
  `ID_PATH=platform-3f980000.usb-usb-0:1.5.3:1.0`

Updated the udev rule so `/dev/magnum-rs485` is keyed to the direct Pi path
`1.2`; `/dev/epever-rs485` remains keyed to hub path `1.5.3`. The CH340 adapters
still have no unique serial, so the software identity follows the physical USB
path, not the dongle body.

## Magnum moved to FT232R adapter for final RS485 trial

Persistent low-single-digit Magnum read errors continued after the CH340 move, so
a final USB-RS485 adapter was added and wired to the Magnum tap:

- FT232R adapter: `/dev/ttyUSB2`, `0403:6001`, serial `BG041BAY`,
  `ID_PATH=platform-3f980000.usb-usb-0:1.5.2:1.0`

A direct `MagnumClient('/dev/ttyUSB2').read()` decoded a sane inverter snapshot
immediately (`INVERT`, 53.6 V DC, 121 V AC out). The now-unwired CH340
`/dev/magnum-rs485` path returned no packet, as expected. Promoted the FT232R to
`/dev/magnum-rs485` using its unique serial and kept the CH340 at path `1.2` as
`/dev/magnum-rs485-ch340` fallback.

Initial supervisor watch was not clean: after the five-minute warm-up, the displayed
Magnum error rate rose from 3.85% to 7.69%. The journal showed four real
`Magnum: no valid inverter packet seen in 10 cycles` failures during the first
seven minutes of the FT232R run (`18:22:59`, `18:24:31`, `18:26:55`, `18:27:34`).
So the adapter change alone did not eliminate the persistent read failures.

Conclusion: revert the canonical Magnum assignment to the direct-Pi-port CH340 at
USB path `1.2`; it had the lowest observed error levels so far. Keep the FT232R as
`/dev/magnum-rs485-ft232r` for future comparison, but do not let it own
`/dev/magnum-rs485`. If the CH340 error rate proves to increase monotonically with
adapter uptime, the next mitigation is a supervisor-controlled USB power cycle of
that port/adapter rather than more adapter swapping.
