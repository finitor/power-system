# 2026-07-11

## Hardening Classic clock recovery for simultaneous power-up

The normal failure scenario is not a Pi-only reboot: the battery bank is turned
off and back on, so the Pi and Classic race through boot together. The initial
helper already retried Classic connectivity and failed open, but its 30-second
window could expire before a slow Classic boot. It also trusted the first valid
timestamp, leaving a narrow chance of observing the main board around the time
the MNGP copied its durable value.

Commit `3168632` extended Classic readiness to 120 seconds and the systemd hard
limit to 150 seconds. A timestamp is now trusted only after samples at least two
seconds apart advance normally. A stopped clock or discontinuous jump restarts
confirmation; the latter is expected behavior if the MNGP transfers time while
the helper is watching. NTP is checked on every retry and again before any
clock set.

The failure boundary remains intentional: if the Classic never boots, never
answers, or never produces stable valid time, the helper exits and the
supervisor starts with the Pi's persisted approximate clock. The clock is still
only advanced, never moved backward. Tests cover stable advancement, an
MNGP-like jump, NTP arriving mid-wait, and a permanently absent Classic. The
full deployment suite passed (486 tests plus 4 subtests), systemd verification
passed on `blueberry`, and a live dry run read the advancing Classic clock.

This session also consolidated the operator procedure and subsystem rationale
so future S31 additions and WAN-less clock recovery do not depend on chat
history.
