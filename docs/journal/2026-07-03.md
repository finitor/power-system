# 2026-07-03

## Blackout-escalation watchdog: burn-in clean, armed

Follow-up to the [2026-06-30](2026-06-30.md) incident that produced the
`offgrid-supervisor-watchdog` service (dry-run reboot escalation when >=3 of
4 real telemetry transports are down for >=10 min — see
[`healthchecks-escalation.md`](../runbooks/healthchecks-escalation.md)).

Plan was to burn it in for ~3 days in dry-run and arm if clean. Checked the
journal from 2026-06-30 08:18 (first run) through 2026-07-03 10:50 (~3 days,
6074 timer-cycle log lines, firing every ~2 min without a missed run or
error):

- Zero `would reboot` entries.
- Zero `degraded`/`recovered` entries at all — the script only logs when a
  quorum breach is observed, so this means the health check never once saw
  >=3 of `classic`/`epever`/`magnum`/`battery` down, not just that it never
  crossed the 600s threshold. Stronger signal than the bar for arming.
- `/api/v1/health` currently reports all checks `ok`.

Armed by adding `SUPERVISOR_WATCHDOG_ARMED=1` to `/etc/offgrid-power.env`
(read fresh each timer run, no restart needed). Confirmed the timer stayed
active and the next cycle ran clean post-arm with no errors and no reboot
(as expected — system is healthy).
