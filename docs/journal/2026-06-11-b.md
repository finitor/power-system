Two features around having two charge controllers serve one staged-charging

## Charge-stage vocabulary normalized

The Classic and EPEver report charge stages in different words, which worked
against treating them as one charging goal — the current taper had been
carrying a kludged set that enumerated both dialects
(`{"Absorb","BulkMppt",...,"Boost"}`). Introduced a canonical vocabulary
(the Classic's, which tracks industry-standard terms) in `charge_stage.py`
and normalized both controllers to it. The taper now keys off canonical
stages only.

Mapping decisions worth recording:
- **EPEver has no distinct bulk stage** — it reports `Boost` for both the
  constant-current climb and the constant-voltage hold. So `Boost` → canonical
  `Absorb` (its literal meaning), and an EPEver reading `Absorb` may still be
  physically in bulk. Flagged this to finitor; he was fine with it.
- **HyperVoc is not Resting.** First pass folded the Classic's
  PV-overvoltage protection state into `Resting`; finitor pushed back — it's a
  protection state and must stay observable. Gave it its own canonical value.
  Surfaced the general point: single-vendor canonical stages are fine; each
  controller's map only emits what it can reach, and the taper's ACTIVE/STOP
  sets ignore unmapped stages (→ no write, the safe default for a protection
  state).

On finitor's instinct that normalization should live low in the stack so
renderers carry no vendor knowledge: reworked the API so each controller's
data block serializes the stage as a `{canonical, vendor}` pair
(`NormalizedStage`), where `vendor` is present **only when it adds
information** beyond the canonical name. All three renderers (web, terminal,
api-terminal) collapsed to one rule via `NormalizedStage.render()` —
"canonical, then vendor in parens if present" — deleting the formatting that
had been copy-pasted three times. No external consumer of that JSON exists
(only `api_terminal_display` and `scripts/diag_api.py`), so the shape change
was free.

## First live EPEver write — charge voltages synced from the Classic

`scripts/epever-copy-from-classic.py` copies the charge voltages (and, unless
`--no-current`, the current limit) from the Classic baseline to the EPEver:
absorb→boost (0x900B), float→float (0x900C), equalize→equalize (0x900A),
current limit→0x9013. The voltage write is a **read-modify-write of the
0x9007–0x9012 block** (function 0x10) that overwrites only those three cells
and preserves the EPEver-only protection thresholds (OVD/reconnect/LVD/
discharge), which have no Classic counterpart. Dry-run by default; aborts if
a target exceeds the EPEver charging-limit ceiling (0x9008).

Applied it: EPEver Boost 57.6→54.4 V, Float 55.2→54.1 V, Equalize 58.3→54.4 V,
max charge 100→80 A. Verified three ways — the writer's own read-back, the
restarted supervisor's live page, and that LVD stayed at 44.4 V (proof the
RMW left protections alone).

**Surprise caught by the dry-run:** the EPEver reports User battery type as
register code **0**, not 6. (`BATTERY_TYPES` maps both 0 and 6 → "User"; the
sniff session had suggested 6.) The first cut of `write_charge_voltages`
hard-checked `!= 6`, so it would have aborted on a live controller that *is*
in User mode, printing the absurd "must be User; reports code 0 (User)". The
dry-run showed `Battery Type: User (code 0)` and gave it away before any
write. Fixed to check the decoded type name. This is exactly the value of the
dry-run-first discipline — the precondition bug never touched hardware.

## Console dropped during the write — made self-healing

Stopping the supervisor to free the EPEver adapter took the desktop console
down with it (`offgrid-console` `BindsTo` the supervisor), and a plain
`start offgrid-supervisor` did not bring it back — the recurring
`BindsTo`-propagates-stops-not-starts footgun. Started it manually to recover,
then fixed it durably: added `Upholds=offgrid-console.service` (systemd 249+;
the Pi runs 257) to the supervisor unit so systemd revives the console
whenever the supervisor is active again. Updated `display-services.md`, which
had previously told us to use `restart` as the workaround.

## Mac venv upgraded to Python 3.12

The local venv was Python 3.10, but `magnum-pi` requires ≥3.11 — so the full
test suite couldn't run on the Mac and I'd been stubbing `magnum_pi` to
exercise the rest. Rebuilt `.venv` on MacPorts `python3.12` (3.12.13),
reinstalled `-e .` plus `pytest`. Full suite now runs natively: 157 passed,
no stub, no ignores — local finally matches the Pi.
