# 2026-06-12 — Logging revision: flat store live on the SSD, ADR 0003 complete

## One canonical store (ADR 0003 phases 2, 3, 5 + cutover)

The logging framework revision landed in one pass, with an accepted
no-logging window during the transition. The three overlapping models are
gone; the flat `metric_samples` EAV time-series plus a hash-keyed `events`
table are now the only write paths.

- **Best-effort recorder:** every store write catches all errors; a store
  that fails to open or write is moved aside (`*.corrupt-<ts>`) and
  recreated; reads degrade to "no data". WAL + `synchronous=NORMAL`.
  Supervision is never affected — the isolation that made the
  integrity-out-of-scope posture safe is now enforced in code.
- **Wider coverage than the JSON-blob era:** `snapshot_metric_samples()`
  now also emits EPEver (`epever.1`, `epever.1.settings`) and Magnum
  sources, which the old snapshot writer recorded only inside the blob and
  the flat path never covered at all. Both controllers emit canonical
  `charge_stage` plus `charge_stage_vendor`. Weather is flat samples too.
- **Events wired:** charger-taper decisions and inverter on/off / LBCO
  cut-outs write to `events`. Notably the `InverterEventTracker` had been
  built and tested but never called from the loop — the CSV it was meant
  to feed had been write-only *and* never written.
- **Retired:** `supervisor_snapshots`, `device_settings_snapshots`, the
  wide `weather_snapshots` table, all telemetry CSVs (load-samples,
  load-soc-baselines, ambient, charger-taper, inverter-events), the
  web-display access log, and the `export_batch_records` ledger + views.
  Old tables remain in the existing DB file untouched for the optional
  phase-7 backfill.
- **State that used to live in CSVs** now derives from the store: the
  rolling load buffer is in-memory and seeded back from `metric_samples`
  at startup; the midnight-SOC baseline is queried from battery SOC
  samples near local midnight (once per day, negative-cached).
- **Merge groundwork (phase 4 partial):** `merge_metric_stores()` does the
  idempotent `INSERT OR IGNORE` union over the content-hash ids. The
  mountpoint-based SSD/SD write-target switch is still to come.
- **R2 exporter re-pointed** to `metric_samples`/`events`, stamping rows
  via their export columns; serialization stays gzipped NDJSON until the
  Parquet swap (phase 6). The export timer remains disabled.

## SSD cutover (phase 1)

`/etc/fstab` repointed from the old removed SSD's UUID (`8d7214f5…`) to
the new 840 EVO (`8e8a4fee…`); store rsync'd over; `/srv/telemetry` now
mounts `/dev/sda1` ext4 `noatime` via the Apricorn bridge on the powered
hub. The SD copy remains shadowed under the mountpoint — harmless, and
it is where the phase-4 fallback will write anyway. Deploy went clean:
167 tests on the Pi, services healthy, flat samples from every source
within the first cadence tick, WAL confirmed, legacy log mtimes frozen.

`sqlite3` CLI installed on the Pi; `diag.sh` now reports store/event
freshness (`store: samples=… newest=…`) instead of tailing retired CSVs.

## Old stores discarded (phase 7 resolved)

Operator decision: skip the backfill, blow away the legacy data for
simplicity. Dropped the legacy tables from the live DB and VACUUMed
(14.4 MB → 416 KB), and deleted the retired CSVs/access log from the
SSD, the shadowed SD copy, and the repo-local `data/` dir on the Pi
(`terminal-display.err.log` kept — the console script still uses it).
The flat store's first samples today are the start of history. Recorder
confirmed writing normally after the wipe.

## Table renamed: `metric_samples` → `samples`

Naming review before any consumers exist: `metric_samples` is 14
characters of redundancy inside a telemetry database, and it will be
typed in ad hoc SQL forever. Renamed to `samples` — short, accurate (a
row is one sample, not one metric), and symmetric with `events`. Export
`record_type` follows (`metric_sample` → `sample`); index names follow
(`samples_*`). Python helper names (`snapshot_metric_samples()` etc.)
keep their descriptive names — they never appear in SQL. Live DB
migrated in place: union today's rows into `samples`, drop the old
table.

## Phase 4 done: SD fallback with merge-on-reattach

The recorder now takes `mountpoint=/srv/telemetry` and
`fallback_path=/var/lib/offgrid/metrics-fallback.sqlite` (SD). The
mountpoint guard exists because the naive failure mode is silent: with
the SSD unmounted, writes to the primary path would land in the
directory shadowed beneath the mountpoint and become invisible on
remount. Writes also fall back when a primary write fails — a yanked
USB device raises `OperationalError`, which now falls back instead of
triggering the corrupt-store discard (reserved for corruption-shaped
`DatabaseError`s). After the next successful primary write the gap is
unioned back (content-hash `INSERT OR IGNORE`) and the fallback file
deleted; merge failures retry next tick. Reads follow the active store.

Verified live on the Pi, not just in tests: lazy-detached
`/srv/telemetry` under the running supervisor (lazy because the console
holds an err-log fd), watched 104 samples accumulate in the SD fallback
over ~90 s, remounted, and saw "Telemetry fallback store merged back:
+104 samples, +0 events" with the fallback file removed — one
supervisor tick per minute straight through the window, no gap.

## Phase 6 done (amended): date-partitioned NDJSON, not Parquet

Hard hardware fact the ADR didn't know: the Pi runs **32-bit Raspbian
(armv7l)**, and pyarrow ships no armv7l wheels — piwheels included,
verified by a failed `--only-binary` install on the Pi. Parquet cannot
be written on this host (and DuckDB itself has no armv7l wheel either).
The decision's *goal* — one query engine spanning local + object
storage — survives without it: DuckDB reads `.ndjson.gz` from S3
natively. So the exporter keeps gzipped NDJSON but adopts the
Parquet-style layout now: one table and one local capture date per
object, hive partitions
(`metrics/{samples,events}/date=YYYY-MM-DD/<ts>-<batch>.ndjson.gz`),
uniform schema per object, oldest date drains first. A future 64-bit
OS upgrade swaps only the serializer, not the layout.

Verified end to end: `offgrid-metrics-export.timer` re-enabled (daily
12:05, kept enabled by deploy.sh); a manual run uploaded 4,180 samples
to `metrics/samples/date=2026-06-12/…ndjson.gz` in B2; and a single
DuckDB session on the Mac queried the B2 partition (`read_json` +
httpfs) and an attached copy of the live SQLite, with the archive∪live
union deduping to exactly the same 40 battery-SOC samples by
content-hash `sample_id` — the idempotency story working as designed.
One footgun for future queries: `read_json` auto-parses `captured_at`
to a UTC timestamp while SQLite returns local-offset text, so CAST
explicitly when unioning across the two.

## ADR 0003 status: all seven phases closed

Cutover (1), best-effort recorder (2), flat write path + events (3),
SD fallback with merge-on-reattach (4, live-tested), legacy writers
deleted (5), date-partitioned export + DuckDB verified (6, amended),
backfill discarded (7). Still parked until log data matters: dedicated
powered SATA adapter, power-loss flush-integrity test.

## Pi 64-bit OS migration prepared, then parked

Started planning the Raspberry Pi OS Lite 64-bit migration because the
32-bit armv7l host is now the limiting factor for modern framework
compatibility: pyarrow/DuckDB wheels already forced the NDJSON exporter
amendment, and local Codex CLI is much more plausible on a 64-bit OS.
Decision: clean image + restore, not an in-place architecture upgrade,
because supervisor downtime is acceptable and the old card can remain
the physical rollback.

Made the migration scripts real:

- `scripts/backup-config.sh` creates a timestamped bundle with local
  secrets/config, rendered systemd units, udev rules, nginx config, SSH
  material, `/srv/telemetry`, `/var/lib/offgrid`, and system manifests.
- `scripts/restore-config.sh` restores from that bundle only with an
  explicit `--apply`.
- `scripts/install-pi.sh` bootstraps the OS package set, venv, editable
  install, sensor extras, and deploy.
- `scripts/health-check.sh` checks architecture, services, timers,
  SocketCAN, stable serial devices, storage, nginx, healthz, and a
  summarized snapshot.

Live backup created and copied off the Pi:
`backups/pi-migration/offgrid-blueberry-20260612T120203Z.tar.gz`
locally, with a copy left under `~/offgrid-backups/` on `blueberry`.
The backup inspected cleanly and includes the environment file, system
config, telemetry store, fallback store, and SSH material.

Current boot media facts before touching anything: `mmcblk0` is a 64
GB-class Samsung card from 2018 (`GC2QT`, 59.6 GiB). Root uses only
7.3 GB, and `/srv/telemetry` is already on the external Samsung SSD 840
EVO 500 GB. Redeployed current 32-bit Pi at `2456d2f`; 171 tests passed
on the Pi, supervisor/console/nginx were active, CAN was up listen-only
at 500 kbit/s, the Kindle nginx path returned 200, and the API snapshot
was fresh and OK.

Migration is parked until a second microSD card arrives. Target is a
128 GB high-endurance microSDXC; the SanDisk High Endurance
`SDSQQNR-128G-GN6IA` is acceptable. Do not overwrite the current
working card; use it as rollback. The resumed path is: flash the new
card with Raspberry Pi OS Lite 64-bit, boot and SSH in, clone the repo,
copy over the backup archive, run `scripts/restore-config.sh --apply`,
then `scripts/install-pi.sh`, `scripts/health-check.sh`, reboot, and
repeat the health check.
