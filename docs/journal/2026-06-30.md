# 2026-06-30

## "Supervisor wedged overnight with an fs error" — it wasn't an fs error

Reported symptom: the supervisor wedged overnight, a console message about
journald, hard power-cycled at ~06:53 EDT. Spent the session reconstructing what
actually happened and hardening against it.

### The logs were gone, so the metrics DB became the flight recorder

First wall: **journald is volatile on this image.** Raspberry Pi OS ships
`/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` with
`Storage=volatile` (journal in RAM, to spare the SD card), so every pre-reboot log
died on the power-cycle. `/var/log/journal` existed but was empty; `rsyslog` isn't
installed either. The console "journald error" the operator saw is unrecoverable for
the same reason — the log explaining the logging failure wasn't persisted.

So the incident was reconstructed from the one thing that *did* survive: the metrics
SQLite on the SSD (`samples`/`events` tables). Lesson: the persistent telemetry DB is
a better post-mortem source than the system journal on this box, until that changes.

### It was not a filesystem failure

The framing said "fs error." Evidence says otherwise:

- Both ext4 superblocks (`mmcblk0p2` root, `sda1` SSD) read `clean` with **zero**
  lifetime error counts (these survive reboots — a real ext4 error would show).
- `metrics.sqlite` (862 MB) passes `quick_check` + `integrity_check`.
- The SSD was **written continuously all night** — the supervisor kept logging
  112 samples / 10 min the entire time. The disk never dropped.

The "fs error" was most likely the EPEver `Modbus Error: [Input/Output]` messages
(they literally say "Input/Output"), or the `[Errno 13] Permission denied:
/var/lib/offgrid/runtime-state.json` line that prints at supervisor startup.

### What actually happened: a USB-bus brownout, and the supervisor went blind

From `samples`/`events`, all four external transports died inside a ~90 s window
around 04:13–04:14 EDT (08:13–08:14 UTC):

- `network.lan_reachable` 1→0 → `status_condition: 'LAN unreachable'` (Classic is
  Modbus-TCP, so it goes with the LAN)
- `EPEver read failed` (RS485/USB-serial), `Magnum read failed` (USB-serial),
  `Battery CAN read failed` (USB-CAN)

These look independent but aren't. **The onboard Ethernet is USB-attached on this
Pi** (`smsc95xx`), sharing the single `dwc_otg` bus with every serial/CAN adapter and
the SSD. Simultaneous loss of eth + RS485 + serial + CAN = *one* USB-subsystem event,
not four coincidences. The supervisor process never crashed — it logged `ok=0` every
cycle for ~2.5 h (which is why the wall display was frozen on stale data, and why
`Restart=on-failure` never fired: the process was alive, just blind).

Trigger: **undervoltage.** `vcgencmd get_throttled` = `0x50000` (under-voltage *and*
throttling have occurred since boot); dmesg shows `Undervoltage detected!` at boot.
The battery bank was fine (53 V) — this is the Pi's own 5 V rail sagging, with the
SSD + bus-powered hub + three adapters drawing through it. USB is the first casualty
of a 5 V dip; the CPU just throttles and limps on. The SD card rode it out because
it's on the independent MMC bus — which is also why it's the right home for
persistent logs (see below).

Surprise worth recording: the **SSD survived** the brownout while the serial/CAN/eth
adapters didn't. Didn't fully chase it; plausibly the usb-storage layer renegotiated
transparently where the tty/CAN drivers didn't.

### Fixes landed this session

- **journald → persistent** on the SD, capped 200 MB (`99-offgrid-persistent.conf`
  overriding the vendor volatile drop-in). Next incident leaves real logs.
- **runtime-state ownership** — the file was `@OFFGRID_USER@:@OFFGRID_USER@ 0600`
  (left by a manual run), unreadable by the `offgrid` service → permission-denied every start, runtime
  state silently lost. Chowned, and `deploy.sh`'s `chown` is now `-R`.
- **Hardware watchdog** codified into the repo (it was armed on the Pi but in no
  config) — `RuntimeWatchdogSec`/`RebootWatchdogSec`, the backstop for a total
  kernel/systemd hang or a reboot that stalls unmounting wedged USB.
- **Blackout-escalation watchdog** (`supervisor-watchdog.sh`), the piece that would
  actually have helped: detects ≥3 of 4 transports down for ≥10 min via
  `/api/v1/health` and reboots to re-enumerate the bus (a process restart can't fix a
  de-enumerated USB bus — only re-enumeration does). **Shipped in dry-run**
  (`SUPERVISOR_WATCHDOG_ARMED` unset); it logs "would reboot" for a burn-in period
  before being armed. Live on the Pi as of this session.

### Hardware root cause (not a software fix)

The undervoltage is the real cause; the watchdog only mitigates. Recommended: a
**powered USB hub** for the SSD + adapters to offload the Pi's 5 V rail, plus a
known-good supply/cable. The watchdog makes the system self-heal; it does not stop
the brownout.

### Loose end surfaced

`deploy.sh` currently fails at the test step: `kindle_details` golden is out of sync
with the render on `origin/main` (from the INV-temp work in `7d94089`/`855fc95` — the
golden wasn't re-blessed in those commits). A partial re-bless is sitting uncommitted
in the working tree. This **blocks clean deploys** and needs a proper `UPDATE_GOLDEN=1`

## Afternoon: Magnum RS485 rewire experiment (item 12)

Rebuilt the Magnum tap as a **direct 6-pin RJ11 breakout** (removed the RJ45
coupler/breakout chain) to attack the item-12 read failures.

**The pin numbers in our own docs were all wrong, and disagreed with each other.**
The bench RJ45-coupler mapping and the `magnum-pi` "pin 1 = Data+" claim both predicted
A/B positions that turned out **backwards**. Verified by meter: on the 6-pin RJ11
breakout, **pos 2 = A (~3.9 V), pos 5 = B (~0.55 V), pos 4 = GND, pos 3 = +14 V**. Only
the voltage signatures are trustworthy across a connector change — never the pin number.

Ran a controlled **A/B/baseline experiment** (matched ~2.2 h windows, `no valid inverter
packet`/hr): baseline (old, grounded) 38.3 → **A (cleaner, no ground) 43.3** → **B
(cleaner + direct ground) 34.4**. The single-variable A→B step (adding ground) cut it
~20% — **the ground reference is the dominant lever**, confirming the 2026-06-17 150R
experiment. Cleanup added ~10% more. B is kept. Also **killed the "termination is the
next experiment" hypothesis**: at 19200 baud over ~4 ft, reflections are physically
negligible (52 µs bit vs ~12 ns round-trip) — it's common-mode/ground, not reflections.

**Measurement gotcha worth remembering:** tried to use metrics-DB `dc_voltage` *count* as
a read-success metric — it isn't. It's the 60 s snapshot cadence (carried-forward
last-good values), which gave it away by producing **identical counts across days**. The
metrics log itself is *truthful* (the reader stamps `captured_at` only on success, and
`INSERT OR IGNORE` dedups a re-emitted stale value into a gap — the carry-forward is
display-only), but the 60 s snapshot is too **coarse** for fine read-health analysis. The
journal (per-event) is the only sensitive signal — and it only reaches back to this
morning (persistence just enabled), so a same-clock 24 h baseline wasn't recoverable.

Evening conclusion after the long wiring/adapter shootout: **the ultimate fix was
swapping the Magnum USB-RS485 adapter, not another wiring variant.** The direct RJ11
breakout and ground reference improved the old PL2303 path, but the display still showed
~3-10% Magnum read errors. Moving the Magnum tap to a CH340 2-wire adapter immediately
dropped the displayed Magnum error rate to 0.0% in short watch windows, with fresh
inverter reads and no new `Magnum: no valid inverter packet` journal entries. Tried both
the newly plugged CH340 and the older spare CH340; both were clean, so the PL2303
SH-U11H path is the suspect component/interoperability issue. Locked in the older
2-wire CH340 as `/dev/magnum-rs485`, retained the PL2303 as
`/dev/magnum-rs485-pl2303` fallback, and keyed the two live CH340s by **physical USB
path** because they have no unique serial: CAN on `1.5.1`, Magnum on `1.5.2`, EPEver on
`1.5.3`. Practical label rule: label the hub ports as the software identity; the CH340
dongles are interchangeable if moved between ports. Follow-up on 2026-07-01: moved the
Magnum CH340 off the powered hub to direct Pi USB path `1.2` for a hub-bypass trial;
EPEver stayed on hub path `1.5.3`.

## Afternoon: battery-CAN wedge — and what actually clears it

Battery CAN dropped ~17:38 during *active charging*. Systematically ruled out: not wiring
(operator wasn't touching it), not power (`throttled=0x0`), not a CAN bus fault (all error
counters zero — the bus was **silent, not noisy**), not a BMS fault (battery still
accepting charge → contactor closed, BMS electrically alive). It was a **silent-at-source
USB-adapter wedge**.

The important, hard-won finding: **this SH-C31G wedge survives both the can-watchdog's
unbind/rebind AND a `USBDEVFS_RESET`.** Only removing VBUS recovered it — a physical
unplug worked (briefly; it re-wedged in ~2 min). So the can-watchdog's "reset complete"
is a **false positive** for this failure class. Then repeated replugging cascaded into a
**hub-level** wedge (`-110` control-message timeouts across EPEver + Magnum + CAN at
once); a **hard power-cycle** cleared everything cleanly.

Open question this leaves: does a *soft* reboot drop port VBUS enough to clear the
firmware wedge, or come back still dead? Unknown — and with the externally-powered hub
likely holding the adapters up through a Pi reset, maybe not. Instrumented the
**supervisor-watchdog with a soft-reboot recovery probe** (records transports before an
armed reboot, logs recovered-or-not after) so the next real wedge answers it. The durable
fix either way is a **PPPS hub + uhubctl** (software VBUS power-cycle) or a SPI CAN HAT
(no USB to wedge).

**Process note (mine to own):** I botched a reboot by fusing the action with a
45-iteration client-side polling loop — the agent environment blocks a foreground
`sleep`, so I'd used SSH connect-timeouts as pacing, which made the command look stuck and
un-cancellable, and forced a hard power-cycle. Lesson: fire-and-forget the action, verify
in a *separate* step.
