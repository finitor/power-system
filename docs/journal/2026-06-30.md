# 2026-06-30

## "Supervisor wedged overnight with an fs error" — it wasn't an fs error

Reported symptom: the supervisor wedged overnight, a console message about
journald, hard power-cycled at ~06:53 EDT. Spent the session reconstructing what
actually happened and hardening against it.

### The logs were gone, so the metrics DB became the flight recorder

First wall: **journald is volatile on this image.** Raspberry Pi OS ships
`/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` with
`Storage=volatile` (journal in RAM, to spare the SD card), so every pre-reboot log
died on the power-cycle. `/var/log/journal` existed but was empty; `rsyslog` isn't
installed either. The console "journald error" the operator saw is unrecoverable for
the same reason — the log explaining the logging failure wasn't persisted.

So the incident was reconstructed from the one thing that *did* survive: the metrics
SQLite on the SSD (`samples`/`events` tables). Lesson: the persistent telemetry DB is
a better post-mortem source than the system journal on this box, until that changes.

### It was not a filesystem failure

The framing said "fs error." Evidence says otherwise:

- Both ext4 superblocks (`mmcblk0p2` root, `sda1` SSD) read `clean` with **zero**
  lifetime error counts (these survive reboots — a real ext4 error would show).
- `metrics.sqlite` (862 MB) passes `quick_check` + `integrity_check`.
- The SSD was **written continuously all night** — the supervisor kept logging
  112 samples / 10 min the entire time. The disk never dropped.

The "fs error" was most likely the EPEver `Modbus Error: [Input/Output]` messages
(they literally say "Input/Output"), or the `[Errno 13] Permission denied:
/var/lib/offgrid/runtime-state.json` line that prints at supervisor startup.

### What actually happened: a USB-bus brownout, and the supervisor went blind

From `samples`/`events`, all four external transports died inside a ~90 s window
around 04:13–04:14 EDT (08:13–08:14 UTC):

- `network.lan_reachable` 1→0 → `status_condition: 'LAN unreachable'` (Classic is
  Modbus-TCP, so it goes with the LAN)
- `EPEver read failed` (RS485/USB-serial), `Magnum read failed` (USB-serial),
  `Battery CAN read failed` (USB-CAN)

These look independent but aren't. **The onboard Ethernet is USB-attached on this
Pi** (`smsc95xx`), sharing the single `dwc_otg` bus with every serial/CAN adapter and
the SSD. Simultaneous loss of eth + RS485 + serial + CAN = *one* USB-subsystem event,
not four coincidences. The supervisor process never crashed — it logged `ok=0` every
cycle for ~2.5 h (which is why the wall display was frozen on stale data, and why
`Restart=on-failure` never fired: the process was alive, just blind).

Trigger: **undervoltage.** `vcgencmd get_throttled` = `0x50000` (under-voltage *and*
throttling have occurred since boot); dmesg shows `Undervoltage detected!` at boot.
The battery bank was fine (53 V) — this is the Pi's own 5 V rail sagging, with the
SSD + bus-powered hub + three adapters drawing through it. USB is the first casualty
of a 5 V dip; the CPU just throttles and limps on. The SD card rode it out because
it's on the independent MMC bus — which is also why it's the right home for
persistent logs (see below).

Surprise worth recording: the **SSD survived** the brownout while the serial/CAN/eth
adapters didn't. Didn't fully chase it; plausibly the usb-storage layer renegotiated
transparently where the tty/CAN drivers didn't.

### Fixes landed this session

- **journald → persistent** on the SD, capped 200 MB (`99-offgrid-persistent.conf`
  overriding the vendor volatile drop-in). Next incident leaves real logs.
- **runtime-state ownership** — the file was `tvetter:tvetter 0600` (left by a manual
  run), unreadable by the `offgrid` service → permission-denied every start, runtime
  state silently lost. Chowned, and `deploy.sh`'s `chown` is now `-R`.
- **Hardware watchdog** codified into the repo (it was armed on the Pi but in no
  config) — `RuntimeWatchdogSec`/`RebootWatchdogSec`, the backstop for a total
  kernel/systemd hang or a reboot that stalls unmounting wedged USB.
- **Blackout-escalation watchdog** (`supervisor-watchdog.sh`), the piece that would
  actually have helped: detects ≥3 of 4 transports down for ≥10 min via
  `/api/v1/health` and reboots to re-enumerate the bus (a process restart can't fix a
  de-enumerated USB bus — only re-enumeration does). **Shipped in dry-run**
  (`SUPERVISOR_WATCHDOG_ARMED` unset); it logs "would reboot" for a burn-in period
  before being armed. Live on the Pi as of this session.

### Hardware root cause (not a software fix)

The undervoltage is the real cause; the watchdog only mitigates. Recommended: a
**powered USB hub** for the SSD + adapters to offload the Pi's 5 V rail, plus a
known-good supply/cable. The watchdog makes the system self-heal; it does not stop
the brownout.
